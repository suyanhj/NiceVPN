# Design

## Context

见 `proposal.md`。当前 VPN 后台由 `main.py` 注册 NiceGUI 页面，`app/ui/pages/` 下 8 个主要页面合计约 7,500 行，`theme.py` 约 4,478 行；防火墙、对端、服务和用户页面同时承担数据读取、页面状态、交互和渲染，重复维护工具栏、卡片、按钮、空状态与弹窗样式。项目已有 NiceGUI 3.18、FastAPI、业务服务和单元测试，不应为了视觉重构引入独立 Vue 工程或改变运维数据格式。

本设计受以下约束：代码注释保持中文；不引入懒加载；复用现有业务服务；危险操作和远程操作不能弱化确认、日志或错误反馈；实施期间各未迁移页面必须继续可用。

## Goals / Non-Goals

**Goals:**

- 用 Quasar 默认组件和主题能力替代大部分页面级 CSS，使项目维护的是设计令牌和少量布局规则，而不是每个控件的细节。
- 建立稳定的 Python UI 组件与数据适配层，让后续页面直接复用页面外壳、工具栏、数据状态、确认和异步反馈。
- 对数据密集页面按需使用 AG Grid，对仪表盘使用 ECharts，同时避免手写业务 JavaScript。
- 将每个页面及其子流程拆成可单独实现、验证和回滚的小任务。
- 通过先建立基线、再逐页迁移、最后删除旧样式的方式降低大范围 UI 重构风险。

**Non-Goals:**

- 不创建独立 Vue、React 或 Node 构建项目。
- 不在本变更中新增多管理员、RBAC、多租户或审批流程；本变更只实现配置驱动、默认关闭的单管理员登录保护。
- 不重写 `app/services/`、`app/models/` 和持久化格式。
- 不强制所有集合使用 AG Grid；流程型、小数量对象保留 Quasar 列表或卡片。
- 不追求装饰性强、影响信息密度或可读性的动画效果。

## Decisions

### 1. 采用 Quasar-first 的单一设计系统

基础按钮、表单、抽屉、页签、菜单、卡片、对话框、提示和布局全部使用 NiceGUI 已封装的 Quasar 组件。通过应用级颜色、组件默认 props/classes 和少量 CSS 变量统一外观，禁止再引入 Bootstrap、Tabler、DaisyUI、Element Plus 或 Vuetify 作为第二套组件系统。

替代方案是接入现成后台 CSS 套件，但会与 Quasar 同时控制表单、弹窗、间距和深色模式，减少不了长期维护量。

### 2. 静态前端资源与 Python 组件明确分层

`theme.py` 只作为主题注册入口，负责应用级 Quasar 颜色、深色模式、组件默认 props/classes 和静态样式加载，不再保存大段 CSS 字符串。静态资源按职责放入 `app/ui/static/`：

- `css/tokens.css`：品牌色、状态色、页面背景、文字层级、间距、圆角、阴影和等宽字体变量。
- `css/shell.css`：导航、顶栏、内容区、响应式断点和对话框尺寸等壳层布局。
- `css/effects.css`：背景网格、轻微边框高光和状态灯等少量科技感效果。
- `js/`：剪贴板、日志滚动等确实只能在浏览器执行、且可跨页面复用的通用行为。
- `vendor/`：Sortable 等固定版本的第三方前端资源，避免与项目自有脚本混放。

Python 文件继续负责组件树、数据绑定、事件回调、业务状态以及 AG Grid/ECharts 的动态配置；业务规则、接口调用和敏感配置不得搬入静态 JavaScript。静态目录可被浏览器直接访问，禁止存放 SSH 私钥、Webhook、口令、用户数据或运行时配置。

组件外观优先由 Quasar props/classes、AG Grid theme 和 ECharts theme 配置，不为每个页面复制 CSS 选择器。旧 CSS 和内联 JavaScript 只有在对应页面验收、确认静态替代资源生效后才分批删除。

### 3. 建立无业务知识的共享 Python 组件层

`app/ui/components/` 负责稳定的呈现模式，不直接调用用户、证书、防火墙等业务服务。预期组件边界包括：

- 应用壳层与导航定义。
- 页面标题、面包屑和操作区。
- 主操作、普通操作、危险操作和更多菜单。
- 状态标识、指标卡、说明卡和数据值展示。
- 加载、空白、无匹配、错误和重试状态。
- 确认对话框、表单对话框和异步操作反馈。
- 数据表格容器、选中状态、批量操作栏和分页摘要。
- 图表卡片及无数据或错误占位。

页面传入文案、数据和回调。相同功能必须复用组件，不通过复制组件源码形成页面变体。

### 4. AG Grid 仅用于数据密集页面

使用 NiceGUI 的 `ui.aggrid` Community 集成，不启用需要商业授权的 Enterprise 功能，不自行加载不匹配版本的前端包。

适用范围：

- 用户：核心身份、分组、启用、在线、虚拟 IP、流量、证书和连接时间列；复杂操作进入详情或更多操作。
- 证书：名称、序列号、状态、到期和选择/批量操作。
- 防火墙中心与对端策略：规则关键字段、启用、优先级、选择、排序和编辑入口；复杂规则表单仍使用 Quasar 对话框。
- 用户组可作为首个简单表格试点；若表格降低根组说明和网段操作的可理解性，则使用统一 Quasar 列表。

不适用范围：

- 对端和服务对象操作密集，保留结构化列表或卡片。
- 设置和初始化是表单/向导。
- 日志使用专用查看器。

列定义、行数据转换、筛选和状态格式由纯 Python 适配函数生成。使用 NiceGUI 支持的事件和方法完成选择、点击、排序与刷新；若某项交互只能依赖大量自定义 JavaScript，则回退到 Quasar 组件，不扩张前端代码面。

### 5. ECharts 只负责可视化，不承载业务状态

仪表盘使用 NiceGUI 的 `ui.echart` 展示在线/服务健康度、流量和状态分布。指标原始值、更新时间和异常状态仍以普通组件呈现，确保图表加载失败时关键信息可读。图表 option 由 Python 构建，并使用统一主题工厂；图表点击只执行已有页面导航。

### 6. 页面状态和业务动作分离

每个页面保留独立状态对象或字段，负责搜索、分页、选择、当前页签、忙碌状态和当前对端等 UI 上下文；实际业务操作继续调用现有服务。逐步将可复用的数据转换和格式化函数移出超大页面文件，但不借 UI 重构修改业务规则。

异步动作统一遵守：开始时设置忙碌并记录关键日志，执行成功后刷新相关区域，失败时恢复控件和保留输入，最终清理定时器或页面资源。新的模块在应用启动时正常导入，不引入懒加载机制。

### 7. 采用可独立验收的渐进迁移顺序

迁移顺序如下：

1. 建立页面与交互基线、依赖能力验证和共享组件测试。
2. 新主题入口、设计令牌、应用壳层和通用组件。
3. 用户页作为第一个业务页面，验证 AG Grid、状态、批量操作和复杂行操作的完整模式。
4. 用户组与证书页，复用用户页已经稳定的数据视图、CRUD、分页和危险批量操作模式。
5. 对端与部署说明，复用卡片、详情、进度和日志模式。
6. 服务页，复用对端状态、日志和配置编辑模式。
7. 防火墙中心规则，再迁移对端策略、远程同步和导入导出。
8. 设置页各页签和初始化向导。
9. 仪表盘放在最后一个业务页面实施，汇总已经稳定的数据与导航入口，并验证指标卡和 ECharts 模式。
10. 跨页面响应式、可访问性、性能和完整回归；最后删除已无引用的旧 CSS 与组件。

每一步只修改目标页面和已建立的共享组件；通过兼容外壳允许新旧页面暂时共存。

### 8. 测试分为配置、组件、页面与关键流程四层

- 纯函数测试：列定义、行数据映射、状态格式、图表 option 和分页计算。
- NiceGUI 用户级测试：组件创建、按钮状态、对话框、选择和回调。
- 页面构建测试：所有路由在代表性数据、空数据和服务异常下可构建。
- 浏览器视觉/交互测试：桌面与窄屏、AG Grid、ECharts、对话框、日志跟随和拖动排序。

业务服务的现有单元测试继续作为结果兼容基线。每个页面任务完成时运行其定向测试，阶段结束时运行 VPN 全量测试和 OpenSpec 严格校验。

### 9. 单管理员登录默认关闭，配置不完整时快速失败

现有配置文件为 `data/config.json`。增加可选的管理员用户名、管理员密码哈希和会话有效期配置：用户名与密码哈希均缺失时关闭认证；两者均存在且有效时启用认证；只配置一个字段或哈希无效时启动失败，禁止静默降级为无认证访问。

密码只使用 `pwdlib[argon2]` 生成和验证 Argon2 哈希，不接受长期保存的明文密码。提供独立命令生成或更新配置所需哈希。会话签名密钥不与管理员密码复用，在认证首次启用时原子生成并持久化到仅服务进程可读的独立文件；认证关闭时不初始化会话中间件。

认证启用后，使用 NiceGUI 官方认证示例同类的中间件和 `app.storage.user` 会话模式保护全部管理页面；只放行登录页、`/_nicegui` 必需资源、favicon 和明确公开的非敏感静态资源。登录成功只保存最小身份状态，退出清空认证状态；跳转目标只接受站内路径。现有 API Basic、一次性下载链接和其他令牌逻辑保持独立。

### 10. 第三方 JavaScript 固定版本并随应用本地分发

允许使用能显著降低维护成本的成熟开源浏览器库，但采用白名单管理：优先使用 NiceGUI 已经提供的 Quasar、AG Grid 和 ECharts，不重复打包；确需补充时将固定版本文件放入 `static/vendor/`，记录名称、版本、上游地址、许可证、用途和 SHA-256，不从 CDN 运行时加载，也不直接修改压缩后的供应商文件。

自有 `static/js/` 只实现剪贴板、滚动、焦点、拖拽适配等浏览器能力封装。业务权限、数据校验、状态判断、服务调用和敏感配置继续由 Python 负责。新增库必须先证明现有 NiceGUI/Quasar 能力无法简洁满足，并在自动化测试中验证离线加载和浏览器控制台无错误。

浏览器能力统一按以下顺序选型，不允许页面自行跳级：

1. NiceGUI 或 Quasar 已有组件、方法和生命周期能力。
2. 浏览器稳定标准 API，且只需直接调用、不形成自维护算法。
3. 项目已经引入的本地开源库。
4. 经许可证、维护状态、体积和安全性评估后新增的本地开源库。
5. 以上均不适用时，才允许编写职责单一、带测试的薄适配层。

当前能力映射确定为：拖拽优先使用 NiceGUI `Element.make_sortable()`，由 NiceGUI 内部集成 SortableJS，不再手工加载重复副本；滚动优先使用 `ui.scroll_area` 的 `on_scroll` 与 `scroll_to`；焦点优先使用 Quasar 对话框的自动焦点管理、`autofocus`/`data-autofocus` 和组件 `run_method('focus')`；剪贴板必须同时支持 HTTPS、localhost 和局域网 HTTP。安全上下文优先使用 `ui.clipboard.write()`，非安全上下文使用固定版本、本地分发的 `clipboard.js` 作为兼容层，不从 CDN 加载，也不继续扩展自有 `document.execCommand()` 实现。

### 11. 首版按明确的数据规模验收

用户和证书页面按各 5,000 条记录以内设计，防火墙规则按中心与对端各 2,000 条以内设计，对端站点按 100 个以内设计。首版使用 AG Grid 客户端数据模型、筛选和分页，并以这些上限构造性能数据进行渲染、筛选、选择、批量操作和刷新验收。

若真实数据超过上述边界或基准测试无法达到可接受交互响应，再单独设计服务端分页、筛选和增量加载；不在首版预先引入两套数据路径。

### 12. 结构化元数据已由独立变更迁移 SQLite

本 UI 变更最初刻意保留 JSON，避免视觉迁移同时改持久化。该后续工作现由 `vpn-sqlite-storage-v1` 独立完成：Users、Groups、Peers 与中心 Firewall Rules 使用 SQLite 单一事实源，旧 JSON 只参与一次性启动迁移。页面层仍只调用 Service，不感知底层数据库。

CCD、Device Bindings、OpenVPN 配置、PKI/CRL、OVPN 成品、远端 SSH chain cache 与运行日志继续保持其天然文件形态，不强行塞入数据库。

## Risks / Trade-offs

- [AG Grid 与现有卡片交互不完全等价] → 先以用户页验证表格模式，再复用到用户组和证书；复杂行操作放入详情或更多操作，无法稳定实现的页面保留 Quasar 列表。
- [防火墙拖动、远程同步和动态编辑复杂] → 将中心与对端策略分阶段迁移，先保持业务服务和表单逻辑不变，再替换数据视图。
- [主题重构产生大范围视觉回归] → 新旧样式并存到逐页验收完成，按引用删除旧选择器，不整体重建或直接清空主题文件。
- [共享组件被做成新的巨型模块] → 按单一职责拆分文件，业务页面只组合，不把业务条件塞入通用组件。
- [过度使用科技特效降低可读性] → 动效与高光仅用于状态和层级，正文对比度、信息密度和操作清晰度优先。
- [AG Grid Enterprise 功能误用导致授权风险] → 只使用 Community 模块和已确认的 NiceGUI 内置版本。
- [长时操作在页面关闭后继续更新失效元素] → 统一页面客户端检查、任务清理和异常处理，日志与轮询视图关闭时停止更新。
- [配置了部分认证字段导致后台意外裸露] → 配置模型在启动阶段严格校验，部分配置或非法哈希直接失败，不允许自动关闭认证。
- [本地第三方脚本陈旧或来源不清] → 固定版本、记录许可证与校验值，升级时单独审查，不在运行时访问 CDN。
- [SQLite 并发写竞争] → 使用 WAL、短事务与 busy_timeout；当前仍按单节点控制器部署，不把数据库放在多主机共享文件系统。

## Migration Plan

1. 在当前分支记录全页面功能清单、测试结果和必要的浏览器截图，不改变业务代码。
2. 添加共享主题和组件，同时保留现有类名以支持未迁移页面。
3. 按既定顺序逐页迁移；每个子任务完成后执行定向测试并核对操作矩阵。
4. 每完成一组相似页面，复查共享组件是否可复用，禁止在后续页面复制前一页面实现。
5. 全部页面验收后，使用搜索确认旧样式和旧组件无引用，再删除无效代码；如需删除或重建文件，先制作可恢复备份。
6. 执行 VPN 全量测试、页面构建测试、浏览器验证和 `openspec validate --strict`。

回滚以页面为单位：共享组件保持向后兼容，单个页面可恢复到迁移前渲染实现而不回退业务服务和数据。发布失败时回退 UI 提交及依赖声明，不迁移或转换用户数据。

## Open Questions

- 最终字体是否完全使用系统字体，还是随应用打包一份可离线使用的中文字体，可在视觉样稿阶段决定，不影响组件架构和任务边界。
- 仪表盘趋势数据在现有持久化信息不足时，可先展示当前快照与分布；是否增加历史采样属于后续独立业务变更。
